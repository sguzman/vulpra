## Accepted source-pinned native result

[**Original native browser fatal-abort → packaged reporter exec CI 41724548163 PASS**](https://github.com/sguzman/vulpra/actions/runs/41724548163), job `126225788733`, artifact **13273831086** (`m3-original-browser-fatal-abort-reporter-exec`), independently downloaded and inspected. Original source commit: `b1482404dfb8b01342990ee99ea3df0f9756b5f7`; full-normal precompiled native Vulpra archive SHA-256: `7aa4f20d1f6058e2ef92d73dec875f3bbfe98ee5a5fe1ea1b11fcb294762069a`. The pinned artifact and source were authenticated before running the actual original executable; no native package was rebuilt or modified.

This test extends the previously successful normal-startup [real original browser → packaged `crashhelper` launch](M3-ORIGINAL-BROWSER-LIVE-CRASHHELPER-20261103.md). Unlike the previous startup-only observer, **this new test intentionally performs an isolated fatal abort** in a throwaway original browser and watches for the separate native `crashreporter` application executable. It does **not** invoke `crashreporter` directly or replace it with a shim.

The native test:
- Runs exactly the original compiled `/original/vulpra` and `/original/crashreporter` as read-only packaged ELF files in a disposable Arch Linux Docker container with `--network none`, a private Weston Wayland compositor, private temporary HOME/profile, no real display/device mounts and all Linux capabilities dropped **before the browser starts**.
- Confirms the original `xpcom/base/nsIDebug2.idl` exposes a fatal `abort` XPCOM method. It also source-checks `toolkit/crashreporter/nsExceptionHandler.cpp::MinidumpCallback`: it calls `LaunchProgram(crashReporterPath.c_str(), minidumpPath)` when reporting is allowed, and Linux `LaunchProgram` does `fork` + `execl(program, program, minidumpPath, nullptr)`. The original Rust `crashreporter` entrypoint is source-checked.
- Starts the actual packaged browser **directly** with the temporary profile and crash-reporting environment. WebDriver attaches to this already running original browser with `geckodriver --connect-existing --marionette-port 2828`. This is essential: WebDriver's ordinary automated Firefox launch injected a `MOZ_CRASHREPORTER_NO_REPORT` value which Gecko captured during startup, making the reporter-launch path ineligible to run.
- Preflights **inside the actual original browser** via chrome-context XPCOM `nsICrashReporter.crashReporterEnabled` and `nsIEnvironment`. The accepted run reported `enabled=true`, `MOZ_CRASHREPORTER_DISABLE` false, `MOZ_CRASHREPORTER_NO_REPORT` false and `MOZ_CRASHREPORTER` present.
- Uses original `nsIDebug2.abort(`test-only marker`, 1)` in privileged browser context. It never counts loss of the WebDriver session alone as successful reporting. An independent std-only Rust process repeatedly samples actual `/proc` runtime identities and observes the original browser **before** the deliberate abort, verifies the private trigger marker, confirms the original browser ELF is gone afterward, and requires the **actual original `/original/crashreporter` executable** with exactly its expected one absolute `.dmp` argument. The argument value, minidump contents, raw PIDs, paths and profiles are not exported. This is bounded original runtime process/argument evidence, not a synthetic report application.
- For the accepted run, the sanitized native evidence showed **74** post-trigger process scans; **5** actual original reporter-executable samples with the source-matched minidump argument; **at most one** simultaneous reporter executable. The original browser exited; no reporter executable appeared before the trigger.
- Accepted **2/2** Rust observer parser/shape unit tests and rejected **6/6** deliberate post-observation summary mutations (wrong reporter identity, missing minidump argument, false browser exit, wrong original archive, claimed egress, forged crash submission). Only the sanitized **1,195-byte JSON** report was uploaded; the artifact ZIP was 759 bytes. No raw crash dump or browser error/crash log was published.

## Earlier unaccepted investigations and the corrected launch method

The initial CI [41722739730](https://github.com/sguzman/vulpra/actions/runs/41722739730) and bounded diagnostic runs [41723164492](https://github.com/sguzman/vulpra/actions/runs/41723164492), [41723206559](https://github.com/sguzman/vulpra/actions/runs/41723206559), [41723759240](https://github.com/sguzman/vulpra/actions/runs/41723759240) and [41723805507](https://github.com/sguzman/vulpra/actions/runs/41723805507) **did not pass**. The initial native browser **did terminate** after the fatal-abort request, but the strict observer found no executable `crashreporter` in thousands of sampled runtime polls. Added safe browser-side preflight isolated the reason: `MOZ_CRASHREPORTER_NO_REPORT` was **nonempty inside the WebDriver-launched original browser**, even though the invoking script had unset it. The subsequent attempt to override it through `moz:firefoxOptions.env` did **not** remove the original browser's reported flag. The original source's `SetExceptionHandler` captures `doReport=ShouldReport()` **at startup**, so clearing it after a session has already started would not test the intended branch.

The accepted correction did not weaken or fake any checks: it **directly launched the genuine archived browser before starting WebDriver**, preserving its test-only clean crash-reporter environment, then attached to that process rather than allowing WebDriver to spawn a reporter-suppressed process. The browser-side preflight passed, and the original packaged reporter's genuine launch was witnessed. Earlier failed runs are not evidence of a Vulpra product defect.
