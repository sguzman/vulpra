## Pinned-XRE offline startup removes dependence on service URL inventory

[Loopback SOCKS profile 284f74c](https://github.com/sguzman/vulpra/commit/284f74c48b522d83d24b674684106ec0597bede6) was **not accepted**: [ordinary-host native CI 41149598338](https://github.com/sguzman/vulpra/actions/runs/41149598338) still failed ten-second startup when the Remote Settings connection went direct to `firefox.settings.services.mozilla.com` and triggered the intact guard. Proxying user JS preferences does not establish that all early Firefox service routes are redirected.

A subsequent exact source audit found `toolkit/xre/nsAppRunner.cpp` at `b1482404`: near line 4945 the command line `-offline` or environment `XRE_START_OFFLINE` sets `mStartOffline`; near line 6070 XRE explicitly invokes `io->SetManageOfflineStatus(false)` then `io->SetOffline(true)` before normal runtime. `netwerk/base/nsSocketTransport2.cpp` at line ~1366 checks `gIOService->IsOffline()` and returns `NS_ERROR_OFFLINE` for non-local sockets *before* the separate `ShouldBlockAddress(...)` fatal test-only guard. This is the source-supported early startup mechanism to run a **real offline browser** in a host-side private Weston graphical smoke without allowing non-local traffic.

The harness now sets `XRE_START_OFFLINE=1` **only on the packaged browser process** and keeps `MOZ_DISABLE_NONLOCAL_CONNECTIONS=1` supplied by the CI launcher. It no longer injects a fake geographic region, Remote Settings URL, or SOCKS proxy user preferences; the profile is created solely by Vulpra, and we still require Gecko's real nonempty `compatibility.ini` marker. The original ten-second same-surface non-null Wayland buffer attach/commit test remains unchanged. This is an intentionally **offline graphical acceptance environment**, not proof of normal online Ubuntu startup, no source modification, no installed Firefox change, and no assertion about Arch/Hyprland. Its actual CI outcome must be checked independently before reporting a native graphical pass.

## Separate online and offline graphical acceptance scopes

The host-side source-defined XRE offline smoke reached the **real** ten-second baseline acceptance step successfully in [CI 41149816090](https://github.com/sguzman/vulpra/actions/runs/41149816090), then proceeded to loader observation. The host-only offline mode must **not** silently alter the previously accepted normal-online, no-egress network-namespace loader/source mapping workloads, which can have different feature activation and loaded libraries.

The `XRE_START_OFFLINE=1` setting is therefore made **explicit opt-in** via `VULPRA_WAYLAND_TEST_OFFLINE=1` in `packaging/test-wayland.sh`; the default is online and explicitly clears any inherited `XRE_START_OFFLINE`. Only `.github/workflows/m3-native-wayland-loader-observation.yml` opts into offline mode for its ordinary Ubuntu host, where the non-local network guard remains mandatory. Its separate GDB fallback also uses offline mode so it cannot simply reproduce an unrelated forbidden service request. All existing network-namespace callers use the unchanged default online semantics. The harness regression workflow now runs two positive mock cases to verify both opt-in offline and unchanged default online, while requiring the existing same-surface frame and genuine native profile initialization for real acceptance.

The controlled host offline and isolated namespace online results are **different workloads** and must remain labeled separately. No online-host fix, target-workstation acceptance, complete M3 dependency graph, or new source removal is inferred.
